# Round 8 - 핵심 개념 정리

> 대기열 시스템 구현에 필요한 핵심 개념들을 학습하고 정리한 문서.

---

## 1. Back-pressure

하류 시스템(DB, PG)이 감당할 수 있는 속도만큼만 상류(유저 요청)를 흘려보내는 원칙.

```
[유저 요청] → [API 서버] → [DB / PG(결제)]
  (상류)        (중류)        (하류)

평소: 초당 100건 → 문제없음
블프: 초당 10,000건 → DB 커넥션 고갈 → 전체 장애
→ "하류가 감당 가능한 만큼만 흘려보내자" = Back-pressure
```

대기열은 이 Back-pressure를 구현하는 대표적인 방법이다.

---

## 2. Rate Limiting vs Queuing

트래픽이 몰릴 때 선택할 수 있는 두 가지 전략:

| 구분 | Rate Limiting | Queuing (대기열) |
|------|---------------|-----------------|
| 초과 요청 | **거부** (429 Too Many Requests) | **보관** (대기열에 적재) |
| 유저 경험 | "나중에 다시 시도하세요" | "잠시만 기다려주세요 (현재 512번째)" |
| 유저 반응 | 새로고침 → 재시도 폭풍 | 기다림 → 순서대로 처리 |
| 적합한 상황 | API 보호, 봇 차단, 일상적 부하 제어 | 행사 트래픽, 유저가 기다릴 의사가 있는 경우 |

**양자택일이 아니다:**
- 대기열에도 상한(cap)을 두어 Rate Limiting 병행 가능
- 봇/비정상 요청은 Rate Limiting으로 사전 차단 → 정상 유저만 대기열 진입

## 3. Redis Sorted Set

대기열의 순번 조회용 자료구조. 순서 보장 + 중복 방지 + 빠른 조회를 모두 만족한다.

| 요구사항 | 필요한 연산 | Redis 명령어 | 시간복잡도 |
|----------|------------|-------------|-----------|
| 순서 보장 | 정렬 | `ZADD key score member` | O(log N) |
| 중복 진입 방지 | 유일성 | Set 특성 (member = userId, 유일) | - |
| 내 순번 조회 | 랭킹 | `ZRANK key member` | O(log N) |
| 앞에서 N명 꺼내기 | 최소값 pop | `ZPOPMIN key count` | O(log N * count) |
| 전체 대기 인원 | 카운트 | `ZCARD key` | O(1) |
| 상위 N명 조회 | 범위 조회 | `ZRANGE key 0 N-1` | O(log N + N) |

**score 설계:**
- `Redis INCR`로 전역 단조 증가 순번을 생성하여 score로 사용.
- timestamp 기반은 동일 ms 충돌 시 member 사전순 정렬이 되어 FIFO가 깨지고, 멀티 인스턴스 clock skew도 문제가 됨.
- INCR은 원자적이므로 동시 호출에도 중복 없이 엄밀한 FIFO 보장.

**순번 용어:**
- `ZRANK`: 0-based (0이 가장 앞)
- `displayPosition = rank + 1`: 유저에게 보여주는 1-based 순번

## 4. 입장 토큰 (Entry Token)

대기열을 정당하게 통과했다는 증명서. 토큰 없이는 주문 API에 접근할 수 없다.

### Lifecycle

```
[발급]  스케줄러가 ZPOPMIN → SET entry-token:{userId} entry-{UUID} EX 300
[전달]  Polling 응답에 토큰 포함 / SSE로 즉시 Push
[사용]  POST /orders 호출 시 X-Entry-Token 헤더에 첨부
[검증]  GET entry-token:{userId} → 토큰 일치 확인
[삭제]  주문 완료 후 DEL entry-token:{userId}
[만료]  5분 내 미사용 → Redis TTL에 의해 자동 삭제
```

### TTL이 필요한 이유

토큰 발급 후 유저가 이탈하면, TTL 없이는 자리만 영구히 차지한다. TTL로 자동 만료시키면 다음 유저에게 기회가 돌아간다.

### 토큰 성격

TTL(5분) 동안 재시도 가능한 입장권. 주문 완료 시 삭제. 기존 주문 도메인의 `userId + requestId` 멱등성과 함께 동작하여 중복 주문을 방지한다.

### 원자적 상태 전이

ZPOPMIN(대기열에서 제거)과 SET(토큰 발급)은 반드시 원자적으로 처리해야 한다. 두 연산 사이에 서버가 죽으면 유저가 대기열에서도 빠지고 토큰도 없는 영구 유실 상태가 된다. Redis Lua script로 원자성을 보장한다.

## 5. 스케줄러 + 처리량 산정

### 스케줄러의 역할

대기열에서 유저를 꺼내 토큰을 발급하는 유일한 주체. 통제된 속도로 꺼내는 것이 Back-pressure의 실제 구현 지점이다.

**멀티 인스턴스 주의:** `@Scheduled`는 각 인스턴스에서 독립 실행되므로, 서버 3대면 발급량이 3배로 증가. 분산 락(ShedLock 등)으로 단일 리더만 실행되도록 보장해야 한다.

### 배치 크기 산정 (역산)

```
DB 커넥션 풀:            50개
주문 1건 평균 처리 시간:  200ms
이론적 최대 TPS:          50 / 0.2s = 250
안전 마진:               70% (기본값, 모니터링 후 조절)
목표 TPS:                175
스케줄러 주기:            100ms (Thundering Herd 완화)
1회 배치 크기:            18명 (175 / 10 ≈ 17.5, 올림하여 18. 실제 발급률 ~180/s)
```

참고: 목표 175와 실제 발급률 ~180의 차이(5명/s)는 유저가 토큰을 받고 즉시 주문하지 않는 경우를 감안하면 실질적 문제 없음.

또한 175 TPS는 **토큰 발급(입장) 속도를 제어**하는 것이지, 주문 API의 순간 TPS를 직접 제어하는 것은 아니다. TTL 5분 동안 유효한 토큰이 누적될 수 있으므로, 주문 순간 TPS는 175를 초과할 가능성이 있다.

## 6. Thundering Herd

토큰을 받은 유저들이 **동시에** 주문 API를 호출하는 문제. 대기열로 평탄화하려 했는데, 토큰 발급 시점에 다시 몰리는 것.

### 완화 전략

| 전략 | 설명 | 효과 |
|------|------|------|
| **발급 간격 분산** | 1초에 175명 한 번에 → 100ms마다 18명씩 | 부하 10배 평탄화 |
| 토큰 Jitter | 토큰 활성화 시점에 랜덤 딜레이 | 유저가 비활성 토큰으로 주문 실패 위험 |
| API Rate Limit | 토큰 있어도 초당 N건까지만 처리 | 대기 후 429 거부 → UX 붕괴 |

## 7. Polling 기반 순번 조회

클라이언트가 주기적으로 서버에 요청하여 순번을 가져오는 방식.

### 응답 구조

```json
{
  "position": 3500,
  "estimatedWaitSeconds": 20,
  "retryAfterMs": 5000
}
```

### 예상 대기 시간 계산

```
예상 대기 시간 = 내 순번 / 175 (안전 마진 적용 TPS)
```

보수적 TPS(175)를 사용. 예상보다 빨리 들어가면 좋은 경험, 늦으면 나쁜 경험.

### 3가지 상태

| 상태 | 조건 | 응답 |
|------|------|------|
| 대기 중 | ZRANK 결과 있음 | position(rank+1) + 예상 대기 시간 + retryAfterMs |
| 차례 도달 | ZRANK null + 토큰 존재 | 토큰 포함 |
| 대기열에 없음 | ZRANK null + 토큰 없음 | 에러 또는 재진입 안내 |

## 8. SSE (Server-Sent Events)

서버가 클라이언트에게 단방향으로 데이터를 Push하는 HTTP 기반 스트림.

### 핵심 구분: 이벤트 vs 상태

| 구분 | 예시 | SSE 적합성 |
|------|------|-----------|
| **이벤트** | "토큰이 발급되었습니다" | 적합 (특정 시점, 특정 유저, 1회 발생) |
| **상태** | "현재 4,523번째입니다" | 비효율적 (100ms마다 전원 변동, 100만명 전체 Push는 비현실적) |

순번은 고빈도·고팬아웃 파생 상태이므로 SSE로 전체에 Push하면 비용이 감소하지 않는다. 토큰 발급 같은 희소 이벤트에는 SSE가 적합하다. 상위 소수(100명 등)에게만 실시간 Push하는 하이브리드 방식이 현실적.

## 9. Polling 주기 동적 조절

순번이 높을수록 Polling 주기를 길게 설정하여 서버 부하를 줄인다.

설계 기준: **예상 대기 시간 대비 유저가 의미 있는 변화를 체감할 수 있는 간격**.

예상 대기 ~9.5분인 유저(100,001번)에게 5초마다 "100,001번째 → 99,101번째"를 알려주는 것은 무의미. (참고: 1,000,000번째 유저의 예상 대기는 약 95분)

## 10. Jitter

동일 주기의 유저들이 정확히 같은 순간에 요청하는 것을 방지하기 위해, 주기에 랜덤한 시간차를 더하는 기법.

### 일반 Jitter

```
retryAfterMs = interval ± jitter
예: 5000 ± 500 → 4500~5500ms 사이에서 유저마다 다름
```

### 초기 Jitter

이벤트 시작 시 100만명이 동시 진입하면 첫 Polling이 몰림. 진입 시 첫 retryAfterMs를 `random(0, interval)`로 설정하여 전체 범위에 분산.

```
일반 Jitter만: 첫 Polling이 interval ± jitter 범위에 집중
초기 Jitter:   첫 Polling이 0~interval 전체에 균등 분산
```

## 11. Graceful Degradation

핵심 인프라(Redis) 장애 시 시스템이 어떻게 동작할지 사전에 정의하는 것.

### Kafka-first 아키텍처

대기열 진입을 Kafka로 먼저 받고, Redis는 순번 조회용으로만 사용하면 Redis 장애 시에도 Kafka에 원본 데이터가 보존된다.

```
정상: User → Kafka → Consumer → Redis ZADD (순번 조회용) → Polling으로 ZRANK
장애: User → Kafka → 근사 순번 계산 (Kafka offset 기반, 보수적) → 서비스 유지
복구: Consumer가 밀린 Kafka 메시지 → Redis 재적재 → 정상 복귀
```

| 전략 | 설명 | 적합성 |
|------|------|--------|
| 전면 차단 | 대기열 서비스 중단 | 안전하지만 서비스 완전 중단 |
| 우회 (bypass) | 대기열 없이 주문 직접 접근 | DB 보호 목적 자체가 사라짐 |
| 로컬 Fallback 큐 | 서버 메모리 큐로 전환 | 스케일아웃 시 서버별 전역 순번 깨짐 |
| **Kafka-first** | Kafka에 원본, Redis는 조회용 | 데이터 보존 + 근사 순번 서비스 유지 |

**"장애가 발생한 뒤에 판단하면 늦다"** — 사전에 정의해두는 것 자체가 핵심.

## 12. 대기 중 이탈 유저 처리

Redis Sorted Set은 원소별 TTL을 지원하지 않아, 대기 중 이탈한 유저는 ZPOPMIN될 때까지 큐에 남아있다. 이탈 유저가 ZPOPMIN으로 꺼내지면 토큰을 발급받지만 사용하지 않고 TTL로 만료된다.

정책: 이탈자를 즉시 정리하지 않고, 토큰 TTL(5분) 만료에 의한 자연 소멸을 허용. 대기열 cap(100만)에 비해 이탈자 비율이 크지 않다면 실질적 문제 없음. 이탈률이 높아지면 Polling 시 liveness 갱신 + reaper 정리 방식 검토.
