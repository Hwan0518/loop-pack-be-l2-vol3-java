## 0) 전 글 고정 규칙 (무조건 지키기)

1) **도입(서사) 3~6줄**: 왜 이 글을 쓰는지, 어떤 상황인지 짧게라도 넣기
2) **한글 헤딩 고정**: `문제 상황 / 재현(또는 분석) / 전략 수립(선택) / 원인 / 해결 / 검증 / 정리` — Decision 타입은 `마주친 문제 / 접근 / 해결` 허용
3) **길이 B(7~10분 컷)**: 긴 표/전문/코드/로그는 **더보기**로 밀어넣기
4) **정리는 짧게**: 3~5줄(시리즈면 “다음 실험 계획” 1~3개 bullet 추가)
5) 감정표현/구어체(B 범위) 허용: `오잉?`, `그럴 리가 없지`, `ㅋㅋ/ㅎㅎ/ㅠㅠ`, `현타`, `맞이해버렸다..`
    - 단, **훅/전환에서 0~2회만** (본문 설명 파트 남발 금지)
6) **긴 글/비교 글은 TL;DR 권장**: 도입 전에 `<blockquote>`로 1~2줄 요약 넣기 (9.4 형식)
7) **내 작업 메타정보는 본문에서 제거**: `round`, `step`, 과제 회차, 내부 진행 순서처럼 독자가 알 수 없는 프로젝트 메타정보는 제목/본문/헤딩에 쓰지 않는다. 독자는 글 자체만 읽어도 이해할 수 있어야 한다.

## 2) 말투(톤) 고정 가이드

### 2.1 문장 호흡

- 문단 짧게(1~3문장), 줄바꿈 자주
- **한 문장을 한 문단으로 잘게 끊지 않는다**
  - 서로 연결되는 2~3문장은 한 문단으로 묶는다
  - **빈 줄은 문장 사이가 아니라 문단 전환에만** 사용한다
  - 강조용 한 문장 문단은 필요할 때만 제한적으로 쓴다
- 결론 먼저 던지고 근거를 붙이기
- 과장 금지(“무조건/100%” 남발 X) → 대신 **한계/대안**으로 처리
- 기본 종결은 **설명형 `-다`** 로 간다
- 다만 실험 과정, 당시 판단, 관찰 결과, 전환점처럼 **맥락상 자연스러운 구간은 `-했다 / -였다`를 섞어도 된다**
- **경험 서술과 판단 기준의 시제를 구분한다**
  - 내가 겪은 상황, 당시 고민, 선택 과정, 변경 이력은 **과거형(`-했다 / -였다 / -됐다`)** 으로 쓴다
  - 글에서 꺼낸 원칙, 판단 기준, 개념, 섹션 소제목은 **현재형(`-다`)** 으로 쓴다
- 중요한 건 **한 가지 종결만 기계적으로 반복하지 않는 것**이다. 문단의 역할에 맞게 종결을 고른다
- 특히 경험 서술에서도 **`했다 / 했다 / 했다` 식 반복을 피한다**
  - `보였다`, `드러났다`, `문제였다`, `자연스럽지 않았다`, `맞았다`, `낫다고 봤다`처럼 문장 역할에 맞는 종결을 섞는다
- 널리 쓰는 기술 용어는 굳이 어색하게 한글화하지 않기: `cache`, `hit`, `miss`, `TTL`, `write-through` 같은 표현은 유지 가능
- 다만 `write-through`, `cache-aside`처럼 글 흐름상 처음 등장하는 개념은 첫 등장에 짧게 설명 붙이기
- `stale`, `blast radius`처럼 독자가 바로 읽기 어려운 영어 표현은 한국어로 풀어쓰기

### 2.2 자주 쓰는 패턴(톤 고정용)

- “개발하다 보면 {상황}이 은근 자주 나온다.”
- “처음엔 {가설}이라 생각했는데, 결론은 반대였다.”
- “여기서 의문이 들었다. `{질문}`”
- “결론부터 말하면, {한 줄 결론}이다.”
- “이번 글에서는 {목표}를 실험/검증해보고 정리해본다.”
- “{상황}의 비용이 얼마가 될지 생각해본 적이 있는가?”

## 3) 공통 골격 템플릿 (전 글 기본 뼈대)

### 3.1 도입(서사) — 고정

- 상황 1~2줄: {왜 이걸 하게 됐는지}
- 문제 1~2줄: {어떤 문제가 터졌는지}
- 목표 1줄: {이번 글에서 해결/검증/비교할 것}
- TL;DR과 도입 첫 2~4줄은 **메타 설명/OG 설명으로 그대로 노출될 수 있다**고 생각하고 쓴다
  - 줄바꿈이 사라져도 읽히게
  - “TL;DR”, “이번 글에서는” 같은 문구 뒤에 바로 핵심 문장이 오게

> 도입 끝나면 바로 본론. (길게 끌지 않기)

### 3.2 본문(한글 헤딩 고정)

- `문제 상황` → `재현(또는 분석)` → `원인` → `해결` → `검증` 순서가 기본
- 선택적으로 `전략 수립`을 `분석` 뒤, `원인` 앞에 둘 수 있다
  - 사용 시점: 대안 비교, 설계 후보 검토, 의사결정 근거 정리 글
- 글 타입에 따라 일부 섹션은 생략 가능(예: Study 글은 재현이 약할 수 있음)

### 3.3 정리 — 고정(짧게)

- 결론 1줄: “결국 {원인/핵심}이었고, {해결/결론}이 먹혔다.”
- 배운 점 2~3개 bullet
- (시리즈면) 다음에 할 것 1~3개 bullet

## 4) 글 타입별 운영(선택)

> 아래 4개 중 하나를 고르고, 선택한 타입에 맞게 “본문 섹션”의 밀도를 조절한다.

### A) TroubleShooting (장애/오류/삽질)

- 핵심: **재현 가능 + 근거 있는 원인 + 해결 후 검증**
- 본문에서 가장 중요한 섹션: `재현/원인/검증`

### B) Study (개념/정리/적용)

- 핵심: **개념을 내 언어로 정리 + 실전 적용 기준**
- 본문에서 가장 중요한 섹션: `문제 상황(왜 필요한지)/원인(개념 구조)/해결(적용법)`

### C) Experiment (비교/실험/검증)

- 핵심: **가설/통제변수/측정지표/결과**
- 본문에서 가장 중요한 섹션: `문제 상황(가설)/재현(절차)/검증(지표)/정리(한계/다음 실험)`

### D) Decision (설계/판단/기준 정립)

- 핵심: **판단 기준을 세운 이유 + 선택지 비교 + 선택 근거**
- 본문에서 가장 중요한 섹션: `분석(기준 도출)/해결(기준별 판단)`
- 기준이 여러 개면 서브섹션 반복 패턴 사용 가능 (5.6 참조)
- 사용 시점: 아키텍처 의사결정, 패턴 도입 기준, 설계 원칙 정리 글

---

## 5) 섹션별 “작성 규칙”(한글 헤딩 기준)

### 5.1 문제 상황

- 증상/현상 1~3개 bullet
- 영향도(왜 중요?) 1줄
- (Experiment면) 가설 1줄 포함

### 5.2 재현

- 재현 절차 Step 1~N (최대 5단계 권장)
- 입력/요청 예시(REST면 curl, 테스트면 Given-When-Then 형태)
- 긴 로그/전문은 더보기로

### 5.3 원인

- 한 문장 결론 먼저: “원인은 {X}였다.”
- 근거(로그/스펙/코드 흐름) 붙이기
- 후보가 있었으면 “후보 → 배제/채택 근거”로 짧게 정리

### 5.4 해결

- 바꾼 것: {설정/코드/구조}를 구체적으로
- 왜 먹히는지 2~4문장
- 긴 diff/전체 코드는 더보기로

### 5.5 검증

- “해결됐다”가 아니라 **어떻게 확인했는지** 적기
- 가능하면 수치/스크린샷/테스트 결과 1개 이상
- 부작용 체크(성능/보안/호환) 1줄이라도
- 검증 서두에서 **비교 축**과 **트래픽 유형**을 먼저 선언한다
  - 예: `AS-IS API / DB 직접 조회 / cache miss-hit`
  - 예: `단건 응답 / 동시 요청 / 지속 부하`
- 검증 소제목은 **무엇을 측정했는지** 바로 보이게 적는다
  - 예: `Read Model + 복합 인덱스 적용 후 DB 직접 조회 성능 (단건 응답)`
- 표 제목에도 **단건 응답 / 동시 요청 / 지속 부하** 중 무엇인지 반드시 적는다
  - 독자가 표만 보고도 측정 종류를 바로 알 수 있어야 한다

### 5.6 서브섹션 반복 패턴 (Decision 타입)

- 판단 기준이 여러 개인 글에서, 각 기준마다 동일한 구조를 반복하는 패턴
- 구조:
  - `<p data-ke-size="size18"><b>기준 제목</b></p>` (서브 헤딩)
  - **한 줄 기준**: 결론을 한 문장으로 먼저 제시 — 독자가 상세 내용 전에 방향을 잡을 수 있게
  - **고민**: 어떤 상황에서 이 기준이 필요해졌는지
  - **선택지**: 어떤 대안들이 있었는지, 각각의 트레이드오프
  - **해결**: 무엇을 택했고, 왜 택했는지 — 고민에서 세운 기준에 비추어 선택 이유를 연결
- 해결 끝에는 구체 사례에서 뽑아낸 상위 개념/원칙을 1~2문장으로 올려줌 (구체 → 추상)
- 서브섹션 내부 라벨(고민/선택지/해결)은 글 톤에 맞게 변형 가능 (예: 마주친 문제/접근/해결)
- 예시: 이벤트 판단 기준 글, 캐시 전략 선택 기준 글, 테스트 격리 원칙 정리 글 등

### 5.7 정리

- 짧게. 진짜 짧게.
- (시리즈면) 다음 실험/다음 글 계획 1~3개 bullet

## 9) 티스토리 HTML 레이아웃 규칙

> **모든 블로그 글은 티스토리 HTML 모드용으로 작성한다.**
> 마크다운이 아닌 **티스토리 네이티브 HTML**로 작성해야 발행 시 렌더링이 100% 일치한다.
> 작성 완료 후 티스토리 글쓰기 → **HTML 모드** → 본문 전체 붙여넣기 → 저장.

### 9.1 발행 워크플로우

1. 본문을 `.html` 파일로 작성 (파일명: `my-{주제}-tistory.html`)
2. 티스토리 글쓰기 → 우측 상단 **HTML** 모드 전환
3. 본문 HTML 전체 복사 → 붙여넣기
4. **기본모드로 전환하지 않고** 바로 저장/발행
   - 기본모드로 전환하면 티스토리가 HTML을 자동 수정할 수 있음

### 9.2 기본 텍스트

- 모든 문단은 `<p data-ke-size="size16">` 태그로 감싼다
- 빈 줄(문단 간격)은 `<p data-ke-size="size16">&nbsp;</p>`로 표현한다
- 한 문단 안에서 줄바꿈이 필요하면 `<br />`을 사용한다

```html
<p data-ke-size="size16">첫 번째 문단 텍스트.</p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16">두 번째 문단 텍스트.</p>
```

### 9.3 헤딩

- **메인 섹션 (h2)**: `<h2 data-ke-size="size26"><b>헤딩</b></h2>`
  - 사용: 문제 상황, 분석/재현, 전략 수립, 원인, 해결, 검증, 정리
  - `<b>` 태그를 h2 안에 포함 (티스토리 기본 구조)
- **서브 섹션**: `<p data-ke-size="size18"><b>헤딩</b></p>`
  - h3/h4 태그가 아닌 **size18 + bold 문단**으로 처리
  - 사용: 해결 내 개념별 분기, 판단 기준 분기, 마주친 문제/접근/해결 등
- **도입부**: 헤딩 없이 바로 서사 시작

```html
<!-- 메인 섹션 -->
<h2 data-ke-size="size26"><b>이벤트에 대한 이해</b></h2>

<!-- 서브 섹션 -->
<p data-ke-size="size18"><b>마주친 문제</b></p>
```

### 9.4 TL;DR (blockquote)

```html
<blockquote data-ke-style="style2">
<p data-ke-size="size16">TL;DR<br /><br /></p>
<p data-ke-size="size16">한두 줄 요약 본문.</p>
</blockquote>
```

- `data-ke-style="style2"`: 티스토리 인용구 스타일
- TL;DR 텍스트 뒤에 `<br /><br />`로 시각적 간격 확보
- blockquote 내부 문단도 `<p data-ke-size="size16">` 사용

### 9.5 섹션 구분선

```html
<hr contenteditable="false" data-ke-type="horizontalRule" data-ke-style="style6" />
```

- 메인 섹션(`<h2>`) 사이에 삽입
- 서브 섹션 사이에는 삽입하지 않음 (같은 부모 섹션 내)
- `data-ke-style="style6"`: 티스토리 기본 구분선 스타일

### 9.6 강조 (Bold)

- 본문 내 핵심 결론/질문/판단 기준: `<b>강조 문구</b>`
- 값 이름, 필드명 등도 `<b>` 사용 (인라인 `<code>` 사용하지 않음 — 티스토리에서 시각적 강조 효과 없음)
- bold 범위를 정확하게 잡는다 — 조사/어미는 bold 밖에 둔다

```html
<!-- 좋은 예 -->
<p data-ke-size="size16">서로 <b>관심사가 다른 작업들이 서로를 알고있기 때문에 발생</b>한다.</p>

<!-- 나쁜 예: 조사까지 bold에 포함 -->
<p data-ke-size="size16">서로 <b>관심사가 다른 작업들이 서로를 알고있기 때문에 발생한다.</b></p>
```

### 9.7 글머리기호

```html
<!-- 비순서 목록 -->
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>항목 1</li>
<li>항목 2</li>
</ul>

<!-- 순서 목록 -->
<ol style="list-style-type: decimal;" data-ke-list-type="decimal">
<li>항목 1</li>
<li>항목 2</li>
</ol>
```

- 비교 항목은 `<ul>` 또는 `<table>` 중 더 읽기 쉬운 쪽을 선택한다

### 9.8 이미지

```html
<p><figure class="imageblock alignCenter" data-origin-width="1172" data-origin-height="838">
<span><img src="이미지URL" width="600" height="429"
data-origin-width="1172" data-origin-height="838"/></span>
</figure></p>
```

- `data-origin-width/height`: 원본 이미지 크기
- `width/height`: 표시 크기 (본문 폭에 맞게 조절)
- `alignCenter`: 가운데 정렬 (기본)
- 이미지 뒤에 `<p data-ke-size="size16">&nbsp;</p>`로 간격 확보

### 9.9 텍스트 정렬

```html
<!-- 가운데 정렬 (마감 문장 등) -->
<p style="text-align: center;" data-ke-size="size16"><b>마감 문장</b></p>
```

### 9.10 표 / 코드 블록

- 표는 HTML `<table>` 직접 작성

```html
<table style="border-collapse: collapse;" border="1" data-ke-align="alignLeft">
<thead>
<tr><th>항목</th><th>Before</th><th>After</th><th>변화</th></tr>
</thead>
<tbody>
<tr><td>응답 시간</td><td>320ms</td><td>45ms</td><td>-86%</td></tr>
</tbody>
</table>
```

- 코드 블록: 티스토리 기본모드에서 코드 블록을 먼저 만들고 HTML에서 확인하는 게 안정적
- 코드 블록 HTML 구조는 티스토리 에디터가 자동 생성하는 형태를 따른다

### 9.11 더보기 (접기)

```html
<div data-ke-type="moreLess" data-text-more="더보기" data-text-less="접기">
<div class="moreless-content">
<p data-ke-size="size16">접힌 내용</p>
</div>
</div>
```

### 9.12 간격 가이드 요약

| 상황 | HTML |
|------|------|
| 문단 사이 빈 줄 | `<p data-ke-size="size16">&nbsp;</p>` |
| 섹션 전환 (큰 간격) | `&nbsp;` 2개 연속 |
| 같은 문단 내 줄바꿈 | `<br />` 또는 `<br /><br />` |
| 메인 헤딩 앞 | `<hr>` 또는 `&nbsp;` |
| 서브 헤딩 앞 | `&nbsp;` 1~2개 |
| 이미지 앞뒤 | 이미지 뒤 `&nbsp;` 1개 |

## 10) 확장 옵션 (필요 시 선택)

> 0)~9) 고정 규칙은 항상 적용.
> 아래 옵션은 **글 성격에 따라 독립적으로 골라 쓴다.** 여러 개 조합 가능.

### 옵션 A: Experiment 전용 헤딩 셋

- 기본 헤딩(`문제 상황/재현/원인/해결/검증/정리`) 대신 사용 가능
- **대체 헤딩**: `배경 / 가설 / 실험 설계 / 결과 / 한계 / 정리`
- 사용 시점: 비교 실험, 정량 검증 글 (4-C Experiment 타입)
- 기본 헤딩과 **혼용 금지** — 한 글에서 하나만 선택

### 옵션 B: 도입부 확장 (배경 서사)

- 기본 도입 3~6줄 대신, 기술 흐름/패러다임 변화를 설명해야 할 때 **~10줄**까지 허용
- 단, 도입 끝에 반드시 **”이번 글에서는 {목표}”** 한 줄로 마무리
- 사용 시점: 기술 트렌드 비교, 버전 마이그레이션, 새 패러다임 도입 배경이 필요한 글

### 옵션 C: 반전/재발견 구조

- 패턴: `초기 결론 → 문제 발견 → 재평가 → 결론 역전`
- Experiment 글에서 서사 장치로 활용
- 검증 섹션을 `1차 결과 / 문제점 발견 / 재검증`으로 분할
- 사용 시점: 가설이 뒤집히거나, 초기 결과가 재평가되는 실험 글

### 옵션 D: 제목 보조 키워드

- 기본: `[키워드] 한 줄 요약`
- 확장: `[키워드] 한 줄 요약(feat.보조키워드)`
- 사용 시점: 주제가 2개 기술에 걸쳐 있을 때 (예: `[JPA] N+1 해결(feat.BatchSize)`)

### 옵션 E: 톤 패턴 추가

- 2.2 기본 톤 패턴에 더해, 아래를 선택적으로 사용:
  - “놀랍게도, {예상과 반대 결과}였다.”
  - “결론은 그렇지 않다.”
  - “{키워드} 시대를 맞이해버렸다..” (시대 훅)
- 감정표현 0~2회 규칙(0번 5항)은 그대로 적용

### 옵션 F: 정량 비교 테이블

- Experiment 글에서 Before/After 또는 A vs B 점수 비교 시 HTML `<table>` 사용 (9.10 참조)
- 본문에 요약 테이블, 상세 데이터는 **더보기**(`<div data-ke-type="moreLess">`)로 분리
- 사용 시점: 정량 지표가 있는 성능/비교 실험 글
