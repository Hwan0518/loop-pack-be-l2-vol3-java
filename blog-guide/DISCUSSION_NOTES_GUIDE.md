# DISCUSSION_NOTES_GUIDE.md

> 설계 논의 과정에서 고민이 길어졌거나, 의미 있는 판단 기준이 드러난 포인트를 **날것 그대로** 기록하는 문서의 작성 가이드.
> 블로그 글(BLOG_GUIDE.md)이나 WIL(WIL_GUIDE.md)의 **원재료**로 활용한다.

---

## 1. 목적

- 설계 회의·구현 중 드러난 **의사결정 맥락**을 휘발되기 전에 포착한다.
- "왜 이렇게 했는가"를 나중에 꺼내 쓸 수 있도록 **판단 근거**를 남긴다.
- 블로그 글 작성 시 "어떤 소재를 쓸지" 고르는 인덱스 역할을 한다.
- 이 문서 자체는 **발행용이 아니다.** 다듬지 않은 날것 기록이다.

---

## 2. 파일 규칙

- 파일명: `{round}-discussion-notes.md` (예: `round7-discussion-notes.md`)
- 위치: `blog-guide/`
- 파일 상단에 아래 헤더 고정:

```md
# Round {N} - 논의 노트 (블로그 소재)

> 설계 논의 과정에서 고민이 길어졌거나, 의미 있는 판단 기준이 드러난 포인트를 날것 그대로 기록한다.
> 이후 BLOG_GUIDE.md / WIL_GUIDE.md 기준으로 블로그 글을 작성할 때 활용한다.
```

---

## 3. 섹션 구조 (항목 1개 = `## N. 제목`)

각 논의 항목은 아래 구조를 따른다. **필수** 필드와 **선택** 필드가 있다.

### 3.1 제목 (필수)

```md
## N. 한 줄 제목 — 부연 설명(선택)
```

- 번호는 1부터 순차 부여
- 제목만 보고 "무엇에 대한 논의인지" 바로 알 수 있어야 한다
- 부연 설명은 `—` (em dash) 뒤에 붙인다
- 예: `## 1. 핵심/부가 로직 분리 기준 — 쿠폰은 왜 핵심 트랜잭션(TX)에 남겼는가`

### 3.2 keyword (필수)

```md
**keyword**: 트랜잭션 분리, 핵심/부가 구분, 이벤트 분리 기준
```

- 쉼표로 구분한 태그 3~5개
- 나중에 블로그 글 소재를 검색할 때 사용
- 기술 키워드 + 설계 개념 키워드를 섞는다

### 3.3 내용 (필수)

```md
**내용**:
{맥락과 상황 설명}
```

- 이 논의가 왜 시작되었는지, 어떤 배경이 있는지 기술
- 기존 구조, 요구사항, 제약 조건 등을 포함
- 길이 제한 없음 — 날것 기록이므로 상세하게 써도 된다

### 3.4 선택지/후보 (선택)

선택지가 있었으면 명시적으로 나열한다. 형식은 자유:

```md
**후보 A: {방법}**
- 장점/단점

**후보 B: {방법}**
- 장점/단점
```

또는 표 형식:

```md
| 기준 | 후보 A | 후보 B |
|------|--------|--------|
| ... | ... | ... |
```

### 3.5 결론 (필수)

```md
**결론**: {선택한 방법}
- 근거: {왜 이걸 택했는지}
```

- **결론을 먼저, 근거를 뒤에** 쓴다
- "무엇을 택했는가" + "왜 택했는가"를 반드시 포함

### 3.6 고민사항 (선택)

```md
**고민사항**:
{결론을 내렸지만 여전히 남는 의문, 트레이드오프, 경계 조건 등}
```

- 결론이 100% 확신이 아닐 때 남기는 메모
- "이런 조건이면 다른 선택이 맞았을 수도 있다" 류의 기록
- 블로그에서 "한계/주의사항" 섹션의 원재료가 된다

### 3.7 교훈/핵심 원칙 (선택)

```md
**핵심 교훈**:
{구체 사례에서 뽑아낸 상위 개념/원칙 1~2문장}
```

또는

```md
**핵심 원칙 — {한 줄 원칙}**:
{설명}
```

- 구체적 결정에서 한 단계 올려서 일반화한 원칙
- 블로그 글의 "정리" 섹션 원재료가 된다

### 3.8 폐기/변경 이력 (선택)

중간에 방향이 바뀌었거나 폐기된 대안이면, 섹션 상단에 명시:

```md
> 이 섹션은 {이전 설계} 시점의 기록이다. 최종안은 {현재 설계}이므로 참고용.
```

## 4. 섹션 간 구분

- 각 항목(`## N.`) 사이에 `---` (수평선) 삽입
- 항목 내부 소제목은 bold 텍스트(`**제목**:`)로 처리 (heading 태그 사용하지 않음)

---

## 5. 작성 원칙

### 5.1 날것 우선

- 문체를 다듬지 않는다. 구어체, 메모체 허용.
- "~인 것 같다", "아마 ~일 것이다" 같은 불확실한 표현도 그대로 남긴다.
- 블로그 글로 전환할 때 다듬는다.

### 5.2 판단 근거를 빠뜨리지 않는다

- "A를 택했다"만 쓰면 안 된다. **왜** A를 택했는지가 핵심.
- 후보를 비교했으면 비교 기준을 명시한다.
- "교과서적 답"과 "우리 프로젝트의 답"이 다르면 그 차이를 기록한다.

### 5.3 의사결정 흐름이 바뀌었으면 변천 과정을 남긴다

```md
**의사결정 흐름 (N단계 변천)**:

1차 설계: "..."
→ 2차 판단: "..."
→ 3차 최종: "..."
```

- 최종 결론만 남기면 "왜 처음부터 이렇게 안 했는지"가 사라진다.
- 변천 과정 자체가 블로그의 좋은 서사가 된다.

### 5.4 코드/로그/수식은 간결하게

- 코드 스니펫은 핵심 부분만 (전체 파일 X)
- 수식이 필요하면 인라인으로: `체감 지연 ≈ Collector lag + Sync lag + 캐시 TTL`
- 상세 코드/로그는 블로그에서 "더보기"로 처리할 소재이므로, 여기서는 요약만

### 5.5 블로그 소재 연결

- 하나의 논의 항목이 블로그 글 하나의 소재가 될 수도 있고, 여러 항목이 하나의 글로 묶일 수도 있다.
- 특정 항목이 어떤 블로그 글에서 사용되었으면, 항목 하단에 메모:

```md
→ 블로그: `my-part1-event-separation.md` 섹션 2에서 활용
```

## 6. 체크리스트 (항목 작성 후)

- [ ] 제목만 보고 무엇에 대한 논의인지 알 수 있는가?
- [ ] keyword가 3~5개 있는가?
- [ ] 내용(맥락)이 충분한가? — 3개월 뒤 다시 읽어도 이해할 수 있는가?
- [ ] 결론 + 근거가 있는가?
- [ ] 후보가 있었으면 비교가 명시되어 있는가?
- [ ] 의사결정이 바뀌었으면 변천 과정이 기록되어 있는가?

---

## 7. 예시 — 최소 템플릿

```md
---

## N. {한 줄 제목} — {부연(선택)}

**keyword**: {태그1}, {태그2}, {태그3}

**내용**:
{맥락과 상황 설명. 왜 이 논의가 시작되었는지.}

**후보 A: {방법}**
- ...

**후보 B: {방법}**
- ...

**결론**: {선택한 방법}
- 근거: {왜 택했는가}

**고민사항**:
{남는 의문, 트레이드오프, "이런 조건이면 달랐을 수도"}

---
```
