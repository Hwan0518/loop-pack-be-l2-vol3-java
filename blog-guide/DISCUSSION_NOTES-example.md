## 1. ZADD NX 사용 여부 — 새로고침 억제 vs 유령 대기자, 어떤 가치를 우선할 것인가

**keyword**: Redis Sorted Set, ZADD NX, 새로고침 억제, 유령 대기자, 대기열 공정성

**내용**:
대기열에 유저를 넣을 때 `ZADD NX`(이미 존재하면 무시)를 쓸지 말지가 첫 번째 쟁점이었다.

NX를 쓰면 새로고침해도 순번이 유지되어 유저에게 공정하지만, 이탈한 유저(유령 대기자)가 순번을 영구히 차지한다. 토큰 TTL(5분)로 자연 소멸된다고 하지만, ZPOPMIN으로 꺼내기 전까지는 대기열에 남아있어 뒤에 있는 유저들의 순번이 밀린다.

실제 대형 서비스(티켓팅 등)를 조사해보니, NX를 사용하지 않고 새로고침 시 뒤로 밀리는 방식을 쓰는 곳이 많았다. 핵심 이유는 "새로고침 억제 효과"였다. 유저가 "새로고침하면 뒤로 밀린다"는 걸 알면 자제하게 되고, 이게 트래픽 폭증 상황에서 중요한 보호 장치가 된다.

**후보 A: NX 사용 (순번 유지)**
- 장점: 공정, 유저 경험 안정적
- 단점: 유령 대기자 문제, 새로고침해도 부담 없어서 불필요한 요청 증가

**후보 B: NX 미사용 + 서버 방어 (ZRANK 확인 후 기존 순번 반환)**
- 장점: 의도치 않은 재진입 방어
- 단점: NX 쓰는 것과 사실상 동일 → 새로고침 억제 효과 없음

**후보 C: NX 미사용 + 서버 방어 없음**
- 장점: 새로고침 억제 효과 (매우 강력한 트래픽 감소 — 100만 유저 × 5회 새로고침 = 500만 → 100만으로 축소)
- 단점: 네트워크 끊김, 브라우저 재전송, LB retry 등 의도치 않은 재진입에도 밀림

여기서 B안을 검토하다가 "이거 NX 쓰는 거랑 뭐가 다르지?"라는 결론에 도달. 서버에서 중복 방어를 하면 새로고침 억제 효과가 사라져서 NX 미사용의 핵심 가치가 없어짐.

**결론**: 후보 C (NX 미사용 + 서버 방어 없음)
- 핵심 근거: 새로고침 억제가 대기열 시스템에서 가장 비용 없이 강력한 트래픽 방어 수단.
- 유령 대기자 참고: NX 미사용이 유령 대기자를 "자연 소멸"시키는 것은 아님. 이탈 유저는 ZPOPMIN될 때까지 큐에 남아있고, 토큰 TTL 만료로 정리됨. 이것은 별도 문제.
- 전제: `POST /queue/enter`는 자동 재시도 금지 (LB/클라이언트 설정). `GET /queue/position`은 영향 없음.

**핵심 교훈 — "같은 기능처럼 보여도, user incentive와 race 특성은 레이어에 따라 달라진다"**:
NX(Redis 레벨)와 ZRANK 확인(서버 레벨)은 결과가 같지만, NX를 안 쓰는 이유 자체가 "새로고침 시 뒤로 밀리게 하려고"이므로 서버에서 방어하면 목적 자체가 모순된다. 또한 B안은 ZRANK→ZADD가 비원자적이라 NX보다 비싸고 불안정한 구현이 될 수 있다.

## 2. Thundering Herd 완화 전략 — 토큰 Jitter와 API Rate Limit을 왜 적용하지 않았는가

**keyword**: Thundering Herd, Jitter, Rate Limit, UX, 발급 간격 분산

**내용**:
대기열에서 토큰을 발급받은 유저들이 동시에 주문 API를 호출하는 Thundering Herd 문제. 3가지 전략을 검토했는데, 2가지를 UX 이유로 기각한 과정이 핵심.

**후보 A: 발급 간격 분산 (100ms × 18명)**
- 1초에 175명 한 번에 → 100ms마다 18명씩
- 부하 10배 평탄화, 구현 단순

**후보 B: 토큰 Jitter (활성화 시점 랜덤 딜레이)**
- 토큰을 발급하되 0~2초 뒤에 활성화
- 문제: Polling 기반에서 유저가 토큰을 받자마자 주문 시도 → 비활성 토큰 → 주문 실패 → 새로고침 → NX 미사용이라 대기열 뒤로 밀림 → 10분 기다린 유저가 다시 처음부터

**후보 C: 주문 API Rate Limit**
- 토큰이 있어도 초당 N건까지만 처리
- 문제: 대기열에서 10분 대기 → 429 거부 → 토큰 TTL 5분 내 재시도 실패 → 토큰 만료 → 대기열 재진입

B와 C를 기각한 핵심 이유가 같다: **"대기열을 통과한 유저는 주문 API에서 실패하면 안 된다."** 대기열은 "기다리면 반드시 된다"는 약속이고, 통과 후 실패하면 그 약속이 깨진다.

재밌는 건 SSE Push의 Jitter는 적용했다는 점. 차이: SSE Push Jitter는 서버→클라이언트 단방향이라 유저 행동에 영향 없음. 토큰 Jitter는 유저가 직접 주문하는 시점에 영향 → UX 문제.

**결론**: 후보 A (발급 간격 분산)만 적용
- 근거: 18명 동시 호출은 DB 커넥션 50개 기준 충분. "정상 부하 상황에서, 대기열 통과 유저는 주문에서 실패하면 안 된다"는 원칙.
- B/C는 일반적으로 나쁜 기법이 아니라, **현재의 Polling 계약과 NX 미사용 재진입 정책에서 부적합**한 것.

**핵심 원칙 — "부하 완화 기법이 downstream rejection으로 나타나면 queue의 약속을 깨뜨릴 수 있다"**:
Jitter라는 기법 자체는 좋지만, "유저 행동에 직접 영향을 주는 곳"에 적용하면 UX가 붕괴된다. 서버 내부(SSE Push 분산)에서 쓰는 것과 유저 대면(토큰 활성화)에서 쓰는 것은 전혀 다른 결과.

## 3. SSE의 실시간성 굴레 — "순번은 상태(state)이지 이벤트(event)가 아니다"

**keyword**: SSE, Polling, 이벤트 vs 상태, 실시간, 하이브리드

**내용**:
SSE가 Nice-to-Have에 있어서 적용하려 했는데, 무한 굴레에 빠졌다. 사고 과정:

```
SSE가 실시간이 맞아?
→ polling이면 아닌데?
→ 그럼 트리거가 뭔데?
→ 대기열에서 n개 꺼내오는거
→ 그때마다 전체에 보내준다고? 100만명인데?
→ Jitter 사용하자
→ Jitter가 실시간이 맞냐?
→ 아니지..
→ 그럼 SSE 왜 쓰지?
→ SSE는 실시간이잖아
→ (처음으로 돌아감)
```

이 굴레의 원인을 분석했더니 **"SSE = 실시간"이라는 전제가 반만 맞기 때문**이었다.

핵심 발견:
- **이벤트**: "토큰이 발급되었습니다" → 특정 시점, 특정 유저, 1회 발생 → SSE 적합
- **상태**: "현재 4,523번째입니다" → 100ms마다 전원 변동 → 전체 Push 불가능

SSE는 **이벤트에 대해 실시간**이지, 순번처럼 **고빈도·고팬아웃 파생 상태**에는 SSE가 계산/팬아웃 비용을 없애주지 못한다. SSE든 Polling이든 주기적 갱신이 될 수밖에 없다. SSE로 순번을 보내면 "서버 측 Polling을 SSE로 쏘는 것"일 뿐.

**의사결정 흐름 (4단계 변천)**:

1차: "SSE로 전체 순번 Push" → 100만명에 불가능
→ 2차: "스케줄러 기반 SSE Push (방법 A/B/C)" → 서버 측 Polling과 동일
→ 3차: "SSE는 토큰 전달에만 사용 + 순번은 Polling" → 토큰 1초 지연이 TTL 5분 대비 무의미
→ 4차 최종: "상위 100명만 ZPOPMIN 트리거로 실시간 Push + 나머지 Polling"

**결론**: 하이브리드 — Queue는 분리하지 않고, Push 대상만 좁힘
- SSE 실시간: 상위 100명 (ZPOPMIN마다 ZRANGE 0 99 → Push)
- SSE 이벤트: 토큰 발급 즉시 Push
- 나머지: Polling

**고민사항**:
- Codex(gpt-5.4)에게 이 하이브리드 방식을 검증 요청 → "현실적으로 성립, 실무에서 꽤 흔한 패턴" 판정
- "cold population은 polling, hot cohort만 realtime 채널, 희소 이벤트만 push"가 전형적인 실전형 설계

**핵심 교훈 — "전달 수단(SSE)과 데이터 특성(이벤트/상태)을 분리해서 생각하라"**:
SSE/WebSocket이라고 무조건 실시간은 아니다. 고빈도·고팬아웃 파생 상태에 SSE를 써도 계산/팬아웃 비용은 줄지 않는다. SSE가 빛나는 건 희소한 "이벤트"를 전달할 때. 상위 소수(hot cohort)에게만 실시간 Push하는 하이브리드가 현실적 타협.

## 4. SSE Push 스케줄러 구조 — full scan vs min-heap vs tier split, 그리고 왜 전부 폐기했는가

**keyword**: 스케줄러, min-heap, ConcurrentHashMap, 동시성, full scan

**내용**:
SSE로 순번을 Push하려면 "언제, 누구에게 보낼지" 관리하는 스케줄러가 필요했다. 3가지 방법을 비교했는데, 논의가 3번 뒤집혔다.

**후보 A: 단일 스케줄러 + 1초마다 전체 순회**
- 모든 emitter 순회, lastPushTime 비교로 건너뛰기
- 장점: 단순, 동시성 없음, 구간 변경 즉시 반영
- 단점: 100만명이면 ~50ms 순회 (추산, 실측 아님)

**후보 B: 단일 스케줄러 + min-heap (nextPushAt)**
- PriorityQueue로 Push 시각이 된 유저만 꺼냄
- 장점: 불필요한 순회 없음
- 단점: 구간 변경 반영 지연(최대 60초), 유저 제거 O(N) (Java PriorityQueue 기준), 한 틱에 몰릴 수 있음

**후보 C: 구간별 스케줄러 분리**
- tier별 Map + 스케줄러 3개
- 장점: 각 구간만 순회
- 단점: 동시성 문제(유저 유실/중복), burst, 승격 지연

처음에는 C가 효율적이라 생각 → 동시성 문제 발견 → A로 전환 → "100만명이면 50ms 부담" → B(min-heap) 검토 → B의 구간 변경 지연 문제 발견 → A로 복귀 → **그런데 이 시점에서 "SSE로 전체 Push 자체가 의미 없다"는 결론에 도달** → A/B/C 전부 폐기.

Codex에게 A vs C 비교 의견을 물었을 때, "방법 3은 burst가 문제. 같은 tick에 해당 tier 전체가 몰려 처리. 평균은 동일해도 피크가 훨씬 높아진다"는 지적이 추가로 있었다.

**결론**: 전부 폐기. SSE는 상위 100명에게만 ZPOPMIN 트리거로 Push하므로 별도 스케줄러 불필요.
- 폐기 이유: 구조적 우열이 아니라, **문제 정의 자체가 변경**됨 ("SSE로 전체 Push" → "상위 100명만 Push").
- A/B/C의 단점 분석은 naive implementation 기준이며, 각각 최적화 여지는 있었음. 하지만 전제가 바뀌어 비교 자체가 무의미해짐.
- 참고: 스케줄러를 폐기해도 emitter registry, timeout cleanup, reconnect 정리 등 SSE 관리 복잡도는 여전히 남아있음.

**핵심 교훈 — "문제를 잘 풀기 전에, 풀어야 할 문제가 맞는지 먼저 확인하라"**:
스케줄러 구조를 최적화하는 데 시간을 많이 썼지만, 결국 "SSE로 전체 Push"라는 전제 자체가 잘못되어 전부 폐기. 해결책을 정교화하기 전에 문제 정의를 재검토하는 게 더 중요했다.

## 5. SSE 연결 임계값 — 고정값 vs 동적 계산, Polling 주기와의 종속성

**keyword**: SSE, 임계값, 동적 계산, retryAfterMs, Polling 주기

**내용**:
하이브리드 SSE에서 "언제 SSE 연결을 시작할지"의 임계값 설정 문제. 처음에는 position ≤ 500으로 잡았는데, Codex가 "현재 Polling 주기와 조합하면 부족하다"고 지적.

```
1001~10000 구간 Polling 주기: 10초
10초 동안 큐 전진: 180명/초 × 10초 = 1,800명
→ position 1,100에서 마지막 Polling → 다음 Poll 전에 100 이하로 진입 가능
→ SSE 힌트를 못 받고 지나칠 수 있음
```

Codex 제안: `threshold = live zone + 발급속도 × 상위 밴드 poll 간격 + 여유분 = 2000~2500`

하지만 이 값이 Polling 주기에 종속되어, 주기를 바꾸면 threshold도 재계산 필요. 동적 계산으로 해결:

```
// live zone(상위 100명) 반영한 수정된 식
etaToLiveZone = ((position - 100) / 175) - currentPollingInterval
if (etaToLiveZone <= 15초): SSE 힌트 포함
```

**결론**: 동적 계산 방식 채택
- 근거: Polling 주기, TPS, 구간 설정을 바꿔도 자동 적응. 계산 자체는 나눗셈 + 뺄셈 + 비교 한 줄.
- 이 값은 "정확한 판정"이 아니라 "hint 경로". SSE 힌트가 빨리 가면 → 연결 몇 개 더 유지 (무시 가능). 늦게 가면 → Polling fallback으로 정상 동작.
- 175/s는 추산값이며, 실측 시 이동평균이나 보수적 하한값으로 대체 검토 가능.

## 6. Polling 구간별 주기 — exponential에서 실용적 타협으로

**keyword**: Polling, 주기 설계, exponential, 부하, UX

**내용**:
구간별 Polling 주기를 설계하면서 여러 방안을 시도한 과정.

처음에는 (3, 10, 30, 60초)로 시작 → "앞쪽 UX를 개선하고 exponential(2, 4, 8, 16초)로 가자" → 계산해보니 뒷구간(16초 × 90만명) 부하가 70,000 req/s로 폭증 → 구간을 7개로 쪼개서 (2, 4, 8, 16, 32, 64초) → 여전히 42,000이고 구간만 늘어남 → 결국 "앞쪽은 짧게(2, 5, 10초), 뒷쪽은 30초로 고정"으로 타협.

스케일아웃 환경에서의 검토:
- 41,000 req/s → 서버 3대 기준 14,000/대 → 여유
- Redis: 41,000 ZRANK/초 → 처리량의 14~41% → 단일 인스턴스 충분

**결론**: (SSE 실시간, 2, 5, 10, 30초)
- 근거: 앞쪽(곧 입장)은 짧은 주기로 체감 개선, 뒷쪽(9.5분+ 대기)은 30초로 부하 억제. exponential 규칙성은 포기하되 실용적 균형.
- 수치는 전부 **추산**이며, 부하테스트 전 가설. 실측 후 조정 필요.
- 서버/Redis 용량 여유 판단("3대면 여유", "Redis 단일로 충분")도 시스템/네트워크/직렬화 비용에 따라 달라질 수 있음.

## 7. Graceful Degradation — 전면 차단에서 Kafka-first 아키텍처로의 전환

**keyword**: Graceful Degradation, Redis 장애, Kafka-first, 근사 순번, 아키텍처 전환

**내용**:
처음에는 Redis 장애 시 전면 차단을 결정했다. 로컬 Fallback 큐는 스케일아웃 시 전역 순번이 깨지고, 우회는 DB 보호 목적 자체가 사라지며, Kafka 전환은 기존 Redis 대기열과의 병합이 불가능하다고 판단.

```
서버 3대로 스케일아웃 → Redis 장애 → 로컬 메모리 큐 전환:
  서버 A: user-1(1번), user-4(2번)
  서버 B: user-2(1번), user-5(2번)
  서버 C: user-3(1번), user-6(2번)
  → "1번"이 3명 존재 → 전역 순번 깨짐
```

그런데 이 시점에서 핵심 질문이 나왔다: **"대기열이 정말로 정확한 실시간성을 보장해야 하는가?"**

이미 ZPOPMIN으로 18명씩 점프하는 순번이라 정확한 1씩 감소가 아님. 유저도 그걸 기대하지 않음. 보수적 근사 순번이면 충분.

이 관점을 적용하면: 처음부터 Kafka에 진입 데이터를 넣고, Redis는 순번 조회(ZADD/ZRANK)용으로만 사용하는 **Kafka-first 아키텍처**가 가능해짐.

**의사결정 흐름 (4단계 변천)**:

1차: "전면 차단" → 안전하지만 서비스 완전 중단
→ 2차: "Kafka fallback (근사 순번)" 검토 → Kafka에는 ZRANK 없어서 순번 조회 불가?
→ 3차: "순번은 계산 가능" 발견 → 초기 순번 - (처리속도 × 경과시간)
→ 4차 최종: "Kafka-first 아키텍처" → 진입을 Kafka로 먼저, Redis는 조회용

**결론**: Kafka-first 아키텍처 채택

```
정상: User → Kafka → Consumer → Redis ZADD → Polling ZRANK
장애: User → Kafka → 근사 순번 (보수적 120명/초) → 서비스 유지
복구: Consumer → Redis 재적재 → 정상 복귀
```

- Kafka에 원본이 있으므로 Redis 장애 시에도 데이터 유실 없음.
- 인증은 서명 기반(HMAC)이므로 Redis 장애 시에도 동작.
- 아웃박스 불필요: DB 상태와 원자적으로 맞출 대상 없음. produce 실패 → 유저 재시도.
- 주문 TPS(175) 변화 없음.

**고민사항**:
- Kafka fallback 시 순번이 근사치라서 "300번이라더니 갑자기 입장" 또는 "1번인데 안 됨"이 가능 → 보수적 계산(120명/초)으로 항상 늦게 표시하여 "예상보다 빨리 입장" = 좋은 경험으로 유도.
- 기존 Redis 유저(장애 시점에 대기 중이던 유저)의 데이터는 유실됨 → Kafka-first이므로 Kafka에 원본 있어 복구 가능.

**핵심 교훈 — "정합성과 공정성이 핵심 가치인 시스템이라도, 요구 수준을 재정의하면 더 나은 degradation 전략이 열린다"**:
"정확한 실시간 순번"이 아니라 "근사 순번이면 충분하다"는 전제 전환이 전면 차단 → Kafka-first로의 아키텍처 전환을 가능하게 했다. 요구사항의 정밀도를 한 단계 낮추는 것이 시스템 탄력성을 크게 높일 수 있다.
